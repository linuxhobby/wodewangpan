## 二、命名规范

**格式：`英文-中文.md`**（英文短横线连接，中文说明，中间一个半角 `-`）。

> **例外**：目录索引文件统一用大写 `README.md`（即本文件），不加中文后缀——它是入口，要一眼认出来。

```
environment-环境与命令速查.md     ✅
content-内容规范.md               ✅
dev-开发注意事项.md                ✅
environment.md                    ❌ 看不出是什么
环境速查.md                        ❌ 必须用英文开头
environment_环境速查.md            ❌ 用短横线不用下划线
```

- 英文部分用**小写单词**，概括「这一篇属于什么」；中文部分说明「具体讲什么」。
- 一篇只讲一个主题。同一主题的补充内容**就地并入**，不要另开一篇（例如「配图补充」「SEO 新结论」）。
- 归档进 `docs/archive/`，命名同样遵守本格式，正文开头标注 `【归档】` 与完成日期。

## 三、写什么 / 不写什么

**写进 `docs/`**：

- **经验**：踩过的坑、为什么这么定、反面教材（例：标签页忘了传 `wide`，整页比全站窄一圈）
- **注意事项**：动某类东西之前必须知道的事（例：卡片模板两端共用，只能改一处）
- **待办**：还没做的优化、已知欠账、下一步
- **总结**：复盘数据、结论与口径（例：正文字数怎么算、各引擎收录现状）
- **skill**：各 skill 的适用场景、触发方式、踩坑

**不写进 `docs/`**（留在根 README 或代码里）：

- 部署步骤、Nginx 配置、cron、访问统计 → 根 `README.md`
- 目录结构、数据格式、构建命令 → 根 `README.md`
- 纯代码约定 → 就近写在源码注释里，`docs/` 只记「为什么这么定」
- 凭据的真实值 → 一律不写进文档，只记「在哪、叫什么」

## 四、统一要求（新增 / 修改文档时照做）

1. **新增文件必须回来登记索引**，否则没人找得到。改动影响面较大时同步更新 [changelog-变更记录.md](changelog-变更记录.md)。
2. **开头三行说清**：这是什么、适用什么、最近更新时间。
3. **结论变了就地改**：不要另开一篇「新结论」，也不要只在对话里更正。被推翻的结论**保留并划掉**（`~~…~~`），注明为什么错，避免走回头路。
4. **同类内容合并**：发现两篇讲同一件事，合并成一篇，不要留两份会漂移的副本。
5. **命令写成可直接复制的 bash 块**；数据给表格 + 更新时间。
6. **交叉引用用相对链接**（`[workflow-入库流程.md](workflow-入库流程.md)`）。引用别的文档时顺手确认链接还有效——改名后最容易留下一堆 404。
7. **任务型文档做完了就归档**：正文精简为「可复用的口径与工具链」，过程清单（逐条 id 之类）删掉，移进 `archive/`，并在索引里标注已归档。
8. **待办集中记在** [todo-待办清单.md](todo-待办清单.md)，不要散在各篇末尾。做完了移到该文件的「已闭环」。
